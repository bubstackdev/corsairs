# Large tensor view/completion contract audit

Read-only investigation of the installed macOS 27.0.1 arm64e CoreAIRuntime, with compiler references targeting arm64. The [manifest](manifest.json) pins the SDK, generated IR, selected native disassembly and exact commands. The cache image UUID is `E2B84906-28D2-39A3-AEF3-9E1AAE1363D7`; no complete extracted dylib digest was obtained. No native target was launched by this audit.

## Established by SDK/compiler/static native evidence

- [Views.swift](Views.swift) and [views.ll](views.ll) establish full-word pointer/count lowering. MutableRawView `_start` returns a pointer, `storageByteCount` returns `i64`, and RawView `bytes` returns `{i64,i64}`. The native Rust calls use x20 for Swift self, x0 for a pointer/count result, and x0/x1 for RawSpan. No 32-bit byte-count truncation was found at this boundary.
- The SDK's exported inline MutableRawView closure invokes the user body with `_start()`, shape and strides. Its mutable span constructor uses `_start()` and `storageByteCount()`. The closure does not introduce an additional synchronization operation.
- [Native view code](raw-view-native.s) and [the span helper](raw-view-span-helper.s) show RawView `bytes` and `withUnsafeBytes` resolving the backing through the same native call targets and adding the byte offset using 64-bit registers. The span getter calculates its count using 64-bit end minus start. The closure route does not contain an additional fence, async migration future, or copy-completion wait absent from the span route.
- [Both run overloads](run-overloads-native.s) reach the same private inference helper at `0x2AAB5015C`, with mode flag w4 equal to one: Inputs call site `0x2AAB5DD24`, dictionary call site `0x2AAB5ED2C`. Both enter the same asynchronous completion helper at `0x2AAB4084C`: Inputs tail `0x2AAB5DE84`, dictionary tail `0x2AAB5EEDC`. The [dictionary inner region](run-dictionary-inner.s) is retained separately.
- The [common completion continuation](run-common-wait-continuations.s) conditionally awaits the exported internal `ComputeStream.reachedSyncPoint(UInt64)` at `0x2AAB40AD8` before returning to its caller. These internal synchronization points do not expose a stream that the application can fence after `run`.
- Native inputs, mutable arguments and their view containers in `owned.rs` remain allocated through `await_native`. Outputs are extracted through the consuming InferenceValue-to-NDArray getter and read while their owned storage is live. The custom task signals completion only after invoking its original native completion function; the waiter joins under a mutex before releasing the caller's task reference. All five audited Rust files matched the frozen large-check build manifest; their hashes are retained in [the initial audit manifest](audit-manifest.json).

## Public contract and available explicit completion

Apple's [Inputs run documentation](https://developer.apple.com/documentation/coreai/inferencefunction/run(inputs:states:outputviews:)-14emi) describes returned output values and contiguous row-major NDArrays. The [dictionary overload](https://developer.apple.com/documentation/coreai/inferencefunction/run(inputs:states:outputviews:)-mqfb) is documented as a convenience form. The [integration guide](https://developer.apple.com/documentation/coreai/integrating-on-device-ai-models-in-your-app-with-core-ai) reads a result view after awaiting the call, with no extra host-readiness step.

The inspected complete Swift interface exposes no public NDArray wait, synchronize or host-copy completion method. Explicit public completion is available through [ComputeStream.currentWorkCompleted](https://developer.apple.com/documentation/coreai/computestream), plus the throwing asynchronous `AsyncValue.ndArray`/consuming `AsyncMutableValue.ndArray` getters used with [encode](https://developer.apple.com/documentation/coreai/inferencefunction/encode(inputs:states:outputviews:to:)). The application must own the actual stream used by encode; fencing an unrelated stream does not establish completion of run's internal work. Wrapping an already returned NDArray in a fresh AsyncValue is not evidence of synchronization with its original producer.

## Runtime observation and unresolved cause

The root's independent immediate-snapshot [Swift reproduction](../rgb345-swift-fast-native.json) failed on the same large Inputs path. Its slower block-by-block comparison had passed. Root diagnostics also found exact host input and native upload/download, then changing partial output snapshots after inference returned. These observations invalidate a Rust-only explanation for the failing case. Static evidence here does not identify whether the framework's internal completion point precedes a background host materialization, whether another native stage remains outstanding, or whether a different large-array backend defect is responsible.

The next justified completion test is inference encoded onto an explicitly owned stream, followed by its stream fence and throwing result readiness before an immediate host snapshot. This audit does not claim that test passed. A sleep, slow hash, repeated read or unrelated-stream fence cannot establish a safe completion contract. No production workaround was added by this investigation.
