# Corsairs v0.2: Krea execution

The acceptance workload is the existing Krea 2 Turbo pipeline. Corsairs supplies general Core AI execution and ownership capabilities; the application layer owns prompts, tokenization, text-row selection, rotary tables, segment wiring, noise, schedules, latent packing, image encoding, asset selection, and residency policy. Asset authoring remains an offline forge task.

## Work order

| Priority | Capability | Acceptance |
| --- | --- | --- |
| 1 | Dynamic signatures | Preserve unresolved descriptor dimensions; validate each concrete call's dtype, rank, fixed dimensions, element count, and storage limits; obtain actual output shapes after execution |
| 2 | Per-model specialization | Typed load options retain CPU/GPU policy and an explicit `expectFrequentReshapes` override, without changing legacy defaults |
| 3 | Native tensor handles | Upload once, chain functions while retaining native NDArray storage, explicitly download with checked strides, and retain storage through dropped futures |
| 4 | Metal execution | Application-owned persistent command queue, shared buffers, output bindings, encode calls, and completion fences with verified ownership |
| 5 | Overlapping asset loads | Independent loads can remain in flight; failure cleanup joins outstanding work before releasing its resources |

An override of `expectFrequentReshapes` does not reproduce fixed-shape offline specialization. Specialized assets must be selected by source-weight identity and exact input shapes, with dynamic original assets as fallback. The current optimized shape is 4,032 image tokens and 20 text-conditioning rows. Low-bit public tensor types are not required for these already-quantized assets.

## First integration milestone

Load all four specialized denoiser segments, run eight steps using saved text/noise fixtures, decode, and match every Swift latent-step and pixel hash. The owned host-copy path is acceptable for this first correctness milestone. Follow with full prompt encoding, native chaining, and Metal execution, recording speed and peak memory at each stage.

Authoritative latents remain float32. Denoiser latent/text inputs are rounded to float16. Euler uses a float32 multiply followed by a separately rounded float32 add, preserving the reference's operation order. The reference schedule and Metal step kernel remain authoritative; no fused multiply-add substitution is permitted.

The existing first-segment readiness record reports byte-exact Swift matches for image carry, text carry, and conditioning. That is a three-output segment comparison, not an eight-step or pixel-parity result. Its 94.5 MiB image carry implies roughly 4.4 GiB of host traffic across three boundaries and eight steps; this is an estimate, not a measured latency.
