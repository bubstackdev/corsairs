# v0.3 inference against published Python b3

On the quiet M5 Max 64 GiB host, matched H3 and Krea calls have similar latency
in Corsairs and the published `coreai-core 1.0.0b3` Python wheel. Small calls
expose about 1 ms of avoidable Corsairs overhead. A lookup-only experiment and
a sampled Rust loop identify repeated dynamic symbol resolution as the main
small-call optimization target. No production optimization is included in this
benchmark change.

## Matched local results

Values below are **milliseconds**, expressed as the range of process medians.
Each process checks every output name, dtype, shape and full byte payload
against the fixed reference after every warmup and measured iteration.

| Warm public API boundary | Corsairs release | Python b3 | Repeats per language |
| --- | ---: | ---: | --- |
| Tiny feedforward, CPU, owned host round trip | 1.134–1.141 | 0.071–0.072 | Three processes × 100 samples |
| Tiny feedforward, GPU-preferred, owned host round trip | 1.520–1.533 | 0.499–0.502 | Three processes × 100 samples |
| H3 functional block, 19,333 rows, retained run plus all output readback | 539.607–651.259 | 559.299–582.978 | Two cooled processes × 10 samples |
| Krea specialized first segment, retained run plus all three output readbacks | 530.949–547.012 | 536.578–547.041 | Two cooled processes × 10 samples |

[The summary](evidence/v0.3-benchmarks/summary.json) retains the selected raw
report hashes, per-process medians and p95s. Languages alternate order within
each workload. Tiny cases have ten warmups; H3/Krea have three. H3 has a
30-second cooldown before each arm; Krea has 15 seconds. The recorded `pmset`
thermal query reported no warning, but clocks, ambient temperature and backend
caches were not controlled. These few processes do not establish a statistically
significant small percentage advantage for either language.

H3 uses the original functional `packed-text-first-functional.aimodel`, ten
source BF16 weight inputs, and `[1,19333,5376]` hidden state. Inputs total about
994 MB and the output is 207,868,416 bytes. This matches the first-step row
geometry of Aether's attempted render, including 49 text rows; it is one
representative block, not all 50 production assets or later-step tables.
Krea uses the unchanged fixed `tower-first.aimodel`, 4,032 image tokens and
20 conditioning rows. Its three output carries total 99,778,560 bytes,
including the 94.5 MiB image carry. Original Swift hashes match exactly.

Both languages use the same model source bytes, input bytes, compute policy and
default reshape option. Public Python b3 cannot set `expectFrequentReshapes`;
the application uses explicit `true` separately. No BF16-to-F16 substitution
is used for H3. Python b3's BF16 constructor path was verified against the
published extension and exercised by the exact-output comparisons.

Corsairs' separately cooled explicit Metal runs, with a persistent queue,
reused input/output buffers and completion fences, measured **558.417 ms H3**
and **537.078 ms Krea**, including output downloads. Python b3 exposes no
equivalent public Metal binding benchmark. These single-process observations
are consistent with the retained-path range; they do not isolate fence cost.

The initial H3 pair without cooldown measured 560.562 ms Rust /641.230 ms Python.
A subsequent exploratory fixed-order phase sweep drifted as high as 863.913 ms
for Rust Metal/readback. Both are retained as
[pair 1](evidence/v0.3-benchmarks/runs/h3-functional-19333/pair-01.json) and
[pair 2](evidence/v0.3-benchmarks/runs/h3-functional-19333/pair-02.json).
The cooled single-phase comparisons were added to reduce that order effect;
the exploratory phase deltas must not be subtracted to attribute costs.

## Small-call overhead

Across three alternating CPU pairs, an ordered worker marker costs only
**2.1–2.2 microseconds**. Uploading the tiny input costs 543–546 microseconds;
downloading it costs 355–357 microseconds. Retained inference without explicit
host readback costs about 780 microseconds versus Python's 40 microseconds.
Thus the worker handoff alone does not account for the excess.

The [source audit](evidence/v0.3-benchmarks/overhead-audit/research.md) finds
**59 uncached `dlsym` calls** along the tiny owned success path, including
repeated metadata, enum-case and Swift task support lookups. The standalone
[lookup experiment](../experiments/c/dlsym_owned_run.c) replays that exact
ordered symbol list without invoking any resolved function. Three executions
of 10,000 batches each measured **1.046–1.052 ms per 59-lookups batch**, or
17.7–17.8 microseconds per lookup. Every resolved address matched its initial
address. The separate volatile pointer-table control cost about 6 ns per batch;
that control is not an implemented cache or a forecast of total inference time.

The [three-second sampled CPU loop](evidence/v0.3-benchmarks/overhead-audit/sample.txt)
also catches the Corsairs worker repeatedly inside `Library::symbol`,
`dlsym` and dyld's recursive export search. The independent probe accounts for
roughly the observed 1.06–1.07 ms owned-call excess, supporting symbol caching
as the first optimization. An actual cache still needs implementation and
before/after verification. The sampled run is excluded from latency summaries.
[Measurements and commands](evidence/v0.3-benchmarks/overhead-audit/measurements.json)
retain all three probe results and the full profiled Rust validation report.

## What this says about Aether

The [read-only Aether audit](evidence/v0.3-benchmarks/aether-audit/audit.md)
found a release executable, BF16 body weights, persistent Metal hidden buffers,
and weights uploaded once. Per-block host copies of the full hidden state are
already avoided. The attempted 960×544, 124-frame render planned 50 body blocks
for each of 50 steps: **2,500 body-block executions**. Scaling one 0.56-second
block across those calls gives about **23 minutes of body work**. This is a
scaling illustration, not a completed-render measurement; blocks, later tables,
co-residency and surrounding work differ.

The retained Aether attempt was stopped after 22 steps, before decoding. Its
journal lacks stage timestamps, so its approximately 26.6-minute launch-to-stop
interval cannot be divided into startup versus denoising reliably. It also
hashes 88.3 GB of asset streams upfront, prepares 2,500 modulation calls,
retains 38.5 GB of body parameter buffers and issues 161 completion-fence helpers
per step. Counts identify profiling targets; they do not measure their costs.

The next useful application measurement separates integrity checks, loading,
conditioning, modulation preparation, parameter upload, each denoising step and
decoding. Capture memory pressure during those stages and profile representative
body encodes in the fully resident application. A 1 ms cost on 2,500 calls is
2.5 seconds; the small-call fix alone does not predict a minutes-scale render
improvement. Costs of the other ABI/fence calls require their own measurements.

## Reproduction and qualification

The [frozen build manifest](evidence/v0.3-benchmarks/build/manifest.json) pins
the release driver, library and source snapshots on macOS 27.0.1 build 26A434,
Rust 1.99 and CPython 3.12.14. The published wheel SHA-256 is
`8db70074eb049b0a86bd263e137ea173f3298f7f1b60ec1a7f7c592f4c26c4a9`.
No production source changed during measurement. New public-API drivers forbid
unsafe Rust. [The protocol](evidence/v0.3-benchmarks/build/PROTOCOL.md) defines
every timer and cleanup boundary. Full input/output validation is untimed;
native/Metal phases without timed downloads still validate via untimed downloads.
Rust drains and Python drops/yields after each sample. These are sequential
public-API measurements with correctness spacing, not kernel-only timings or
streaming throughput. GPU preference does not identify operator placement.

```sh
python3 -B scripts/benchmark_v03.py \
  --case docs/evidence/v0.3-benchmarks/cases/h3-functional-19333.json \
  --pair 6 --phases native_run_download --cooldown 30 --deadline 100
python3 -B scripts/summarize_benchmark_v03.py
```

Use a permitted native launch context with the pinned reference dependencies,
the frozen compiled driver, external model/fixture files and a fresh pair number.
The benchmark controller enforces child deadlines and joins timed-out children.
Its identity and before/after virtual-memory/thermal observations are recorded
per report. Native calls ran as untraced children of a REA-observed Python
controller; the entry breakpoint precedes timing. No GPU tests ran concurrently.

These measurements predate the [symbol cache](v0.3-symbol-cache.md) and
GPU completion-stream repair. The isolated cache experiment reduces tiny CPU
owned calls from about 1.18 ms to 34 µs. Final release regression evidence is
listed in [the release record](v0.3-release.md). Historical raw measurements and
failed observations remain unchanged. The 4.27 GB RGB lifecycle is outside
v0.3's supported 2 GiB GPU inference boundary; 4 GiB storage and CPU execution
remain available.
