# Corsairs v0.5.0

v0.5 adds image and pixel-buffer I/O and creator-defined asset metadata, and
removes the deprecated `DType::ALL`. It retains every v0.4 bound, path and
known exclusion.

## Changes from v0.4.1

- **Image I/O.** Functions with packed `24RGB`, `32ARGB` and `32BGRA` image
  inputs and outputs load and run on CPU-only, GPU-preferred and Neural
  Engine-preferred compute. The new API is `PixelFormat`, `Image` (tight or
  padded rows), `ImageMap`, `ImageDescriptor`,
  `FunctionDescriptor::{image_inputs, image_outputs}`, `RunResult::images`,
  `Function::run_with_images` and the CLI's `--image NAME FORMAT WxH FILE`.
  Bytes stay in CoreVideo memory order. Planar 4:2:0 traps Core AI, so every
  format other than the three packed ones is described but rejected before any
  buffer exists ([image I/O](image-io.md)).
- **Creator-defined metadata.** `AssetMetadata::creator_defined` returns
  `creatorDefinedMetadata` as a `BTreeMap<String, CreatorValue>`, read-only,
  and `corsairs inspect` prints it. Core AI returns the JSON type it reads back:
  `0`, `1` and `-0.0` arrive as `Bool`, and whole numbers as `Integer`. Content
  beyond 512 levels of nesting, 65,536 values or 16 MiB of string data returns
  `Error::Unsupported` ([creator-defined metadata](creator-metadata.md)).
- **New error:** `Error::InvalidImage`.

### Breaking changes

- `DType::ALL` is removed; use `DType::all()`.
- `FunctionDescriptor` and `RunResult` gain fields and are now
  `#[non_exhaustive]`, so struct literals and exhaustive destructuring outside
  the crate no longer compile.
- `load_function` now succeeds on image signatures that previously returned
  `Error::Unsupported`.
- `AssetMetadata` no longer implements `Eq`, because `CreatorValue` can hold an
  `f64`. `PartialEq` remains.

## Release gates

Recorded on macOS 27.0.1 (26A434) with Rust 1.99.0:

- `cargo fmt --all --check`, clippy with `-D warnings` and rustdoc with `-D warnings`
- `cargo test --offline -p corsairs --no-default-features -- --include-ignored`:
  73 library tests, including the native image round trip on every backend and
  the creator-metadata fixture, nesting and limit tests, plus CLI and doctest;
  31 Python reference tests, including the image fixture-integrity regressions
- `scripts/check_v01.py --native --cycles 10000 --loads 100 --dropped 100`:
  181 positive and 24 typed negative public-API configurations across three
  backends with full stress, in debug and release
- `scripts/check_v02.py --native`: native-handle parity 181/181 and Metal parity
  362/362, plus dynamic-shape and handle drivers, in debug and release
- `scripts/check_images.py --soak 10000 --drop 100`: the frozen fixture manifest
  is verified first, then 123 runs and 30 checks are byte-exact against
  `fixtures/parity-v05/images` on three backends. A 10,000-cycle soak grew at
  most 160 KiB after warmup, and 100 drop and 100 cancel cycles ran per
  backend ([report](evidence/v0.5/image-parity-release.json))
- `scripts/check_creator_metadata.py --soak 20000`: calibration against IR, SIL
  and SDK symbols; Rust matches the Swift oracle on 83 repository assets and
  18 edge assets, including all three 511-deep shapes on the debug CLI; RSS
  is flat over 20,000 inspections ([report](evidence/v0.5/creator-metadata/check-release.json))
- `scripts/check_float8.py`: 0 mismatches over all encodings and 1,002,151
  binary32 inputs in debug and release ([report](evidence/v0.5/float8-conversion.json))
- BF16 driver: 46 configurations, 104 exact values and all 65,536 raw encodings
  in each profile ([summary](evidence/v0.5/bf16-native.json))
- Large tensors against the independent Swift reference, release profile: exact
  2 GiB GPU-preferred and 4 GiB CPU boundaries
  ([GPU](evidence/v0.3-large-tensors/v0.5-release/gpu-limit-f32-gpu-preferred-release.json),
  [CPU](evidence/v0.3-large-tensors/v0.5-release/limit-f32-cpu-release.json))
- `scripts/check_package_v03.py --native` (now accepting 0.5.x): every archive
  member, extracted-package and isolated-consumer builds, eight native
  examples, and packaged CLI and BF16 checks
  ([candidate verification](evidence/v0.5/package-verification.json))

As for v0.4, the H3/Krea external-asset gates, the other large-tensor shapes,
GPU rejection boundaries and benchmarks were not rerun. Images were qualified
only at small sizes (2×4 and 3×5 in the gate; 2048×2048 and 20000×2 in review
probes). The Swift-oracle and b3 image reference runs were not repeated.

## Publication

On 2026-10-18, `v0.5.0` was tagged at merge commit
`414e7c13f01266717c0e3671628c959286d96d08` and published to
[crates.io](https://crates.io/crates/corsairs/0.5.0) with `cargo publish --locked`.
The clean-commit package passed the same native package qualification
([clean verification](evidence/v0.5/package-clean-verification.json)). Its only
changed member relative to the candidate is `.cargo_vcs_info.json`. A first
`v0.5.0` tag pushed before the release PR merged was deleted before any upload.

The [published archive](../dist/corsairs-0.5.0/corsairs-0.5.0.crate) has 57 members,

`1c0124742e29b0e29bf389415f7d9eae0e8c850ec10249198098053e9b2f715c`.

matches. A fresh default-feature consumer resolved `=0.5.0` through Cargo with
unsafe code forbidden. It passed the v0.4 checks, plus BGRA32 image identity on
all three compute preferences and creator-defined metadata.
